[Heading 1.1] 1	Introduction
[Heading 1.3] 1.1 	Background
[Normal] The North-West University (NWU) Potchefstroom Campus currently manages squash court bookings through a physical computer located at the squash courts. Students who want to check court availability or make a booking must therefore travel to the facility first. This limits advance planning, can result in unnecessary trips, and provides limited support for managing cancellations and booking conflicts. The current process also provides limited information about the actual utilisation of the squash facilities (PukSquash Project Team, 2026; Van Niekerk, 2026). 
[Normal] In addition, structured private coaching is not currently managed through a central system where students can view coach availability and reserve coaching sessions. The PukSquash Business Case identified improved student access, better court utilisation and broader access to squash coaching. The Business Case and Feasibility Study evaluated alternative solutions and identified a custom-built web application as the most suitable approach for the project (PukSquash Project Team, 2026; Van Niekerk, 2026). 
[Normal] The development of PukSquash also supports NWU's broader move towards digital services. NWU's Digital Business Strategy promotes the development of integrated technology platforms and improved digital experiences for students and other university stakeholders (North-West University, 2023). 
[Normal] PukSquash is therefore proposed as a centralised, responsive web-based application through which authorised users can view live court availability and make bookings remotely. Court availability will be presented using predefined one-hour time slots. The accepted system design supports Open, Locked and Private Coach bookings and three primary application roles: USER, COACH and ADMIN. 
[Heading 1.3] 1.2	Objective
[Normal] The objective of this Functional Specifications document is to define the required behaviour and functionality of the PukSquash Squash Court Booking System. It provides a functional description of what the application must do, how users interact with it and the rules that must be applied when managing court availability, bookings, coaching sessions and administration.
[Normal] The primary objective of PukSquash is to provide NWU Potchefstroom Campus users with a secure, reliable, and user-friendly method of viewing court availability and managing squash court bookings remotely.
[Normal] The application must also protect the personal information that it processes. User details such as names, email addresses and student numbers or any personal information and must therefore be processed with appropriate access control and security in accordance with the Protection of Personal Information Act 4 of 2013 (POPIA) (Information Regulator South Africa, 2026). 

The objective is also to guide the development of PukSquash towards a feasible and practical solution that can be completed within the available resources, technical capabilities, and realistic project timelines, while still meeting the expectations of the relevant stakeholders. The phased implementation approach supports this by prioritising the essential booking functionality in Phase 1 before introducing additional management and payment functionality in Phase 2.
[Normal] Although PukSquash is currently intended for squash court bookings at the NWU Potchefstroom Campus, the system should be designed with flexibility and future expansion in mind. The underlying booking concepts, such as users, facilities, fixed time slots, availability and reservations, could later support other NWU sporting facilities such as tennis, padel or similar court-based sports, should the university decide to expand the platform. The current Functional Specifications, however, remain focused specifically on the PukSquash Phase 1 and Phase 2 requirements.
[Heading 1.3] 1.3	Scope
[Normal] The scope of PukSquash is the design and development of a responsive browser-based squash court booking system for the NWU Potchefstroom Campus. The system will be implemented in phases so that the essential booking functionality is established before additional management and payment functionality is introduced.
[Normal] Phase 1 includes the core operational functionality of the application:
[Normal] User registration, login and profile management. 
[Normal] User, Coach and Admin role-based access. 
[Normal] Live court availability. 
[Normal] Fixed one-hour court-booking time slots. 
[Normal] Open, Locked and Private coach bookings. 
[Normal] Joining an eligible Open booking. 
[Normal] Viewing upcoming bookings and cancelling bookings. 
[Normal] Coach availability management and the Coach Availability Notice Board. 
[Normal] Administrator management of users and courts. 
[Normal] Court Active or Inactive status. 
[Normal] Backend validation and booking-conflict prevention. 
[Normal] Phase 2 extends the application with registration payments and private coach payments through PayFast, booking and coaching history, administrator booking management, fixed time-slot management, configurable booking rules, registration payment records and NWU Squash Team Practice sessions. Team-practice functionality will allow coaches to reserve multiple available court and time combinations while still preventing the use of inactive courts or already-reserved booking cells. 
[Normal] The current technical scope uses Vue 3 for the web interface, Firebase Authentication for user authentication, a Laravel REST API for server-side business logic and validation, and Cloud SQL PostgreSQL for relational application data. Vue is designed for component-based web user interfaces (Vue.js, 2026), while Firebase Authentication provides authentication services for web applications and supports identity tokens that can be verified by backend services (Google Firebase, 2026). Laravel provides support for API routing and protected server-side application routes, and Firebase SQL Connect provides integration with PostgreSQL-backed relational database (Laravel, 2026; Google Firebase, 2026). 
[Normal] PayFast is introduced during Phase 2 for the agreed registration and private-coaching payment processes. Its developer platform supports custom web-payment integration and server-to-server API communication (PayFast, 2026). 
[Normal] The current approved scope does not include native Android or iOS applications, NWU Single Sign-On, automated reminder functionality, general analytics dashboards or expansion to other sporting facilities. These may be considered as future enhancements but are not part of the current scope.

[Heading 1.2] 2.1	Product Context
[Normal] PukSquash is an online, responsive, web-based application for booking squash courts and coaching sessions intended for the North-West University (NWU) Potchefstroom campus squash facility. The system will replace the current physical booking process, where students must visit the squash courts and use a single computer to view court availability and make bookings. As a result, the current process limits students’ ability to access and book the squash courts conveniently, causing unnecessary travel.
[Normal] The proposed online web application will allow students to remotely view court availability, make and manage bookings from their own devices. The system will support live court availability, self-service court bookings and cancellations, coaching session bookings, and will include a mechanism to prevent conflicting or duplicate reservations. The system will also expand coaching availability by making it available to any NWU student instead of being restricted to the NWU squash team only.

[Heading 1.4] 2.3.2	Court Availability and Booking
[Normal] The main function of PukSquash is to allow users to view court availability and reserve squash courts remotely.
[Normal] Court Availability:
[Normal] The user must be able to select a booking date using a calendar or date picker. 
[Normal] Court availability must be displayed using a grid where:
[Normal] Rows represent predefined one-hour time slots, and columns represent squash courts. 
[Normal] Each grid cell represents one specific “court + booking date + time” slot combination. 
[Normal] Availability must be calculated from: 
[Normal] The status of the court, the status of the time slot and existing confirmed bookings. 
[Normal] An Inactive court must not be available for new bookings. 
[Normal] Court Bookings:
[Normal] The system must support three normal booking types:
[Normal] Open Booking
[Normal] A USER may reserve an available court as an Open booking. The user who creates the booking becomes Player 1. An Open booking with only Player 1 must remain available for one additional player to join. A second authenticated USER may join the same booking. Joining an Open booking must update the existing booking and must not create another court reservation. Once Player 2 joins, the booking becomes Full and no additional player may join. 
[Normal] Locked Booking
[Normal] A User may reserve an available court as a Locked booking. The booking must not allow another user to join. The selected court and time slot remain reserved for the user until the booking is cancelled or completed. 
[Normal] Private coach Booking
[Normal] A User may select Private Coach when reserving a court. The system must show only coaches who have published availability for the selected date and time slot. The user must then select an available coach before confirming the booking.
[Normal] The system must reserve both the court and the selected coach for that period and, no other player may join a Private Coach booking. 
[Normal] Before any booking is created or updated, the backend must validate the court, date, time, player and, where applicable, coach to prevent booking conflicts.

[Heading 1.1] 3	Functional Requirements
[Heading 1.2] 3.1	Purpose / Description
[Normal] The PukSquash web application aims to provide a responsive and accessible platform through which users can remotely view squash court availability and manage squash court bookings at the NWU Potchefstroom Campus. Court availability is based on fixed one-hour time slots, with each court and time-slot combination representing a reservable booking cell. The system should allow users to:
[Normal] Register and log in: A new account is created with the User role. After login, the system determines the stored role and directs the user to the appropriate User, Coach or Admin dashboard.
[Normal] View live court availability: Users can select a date and view the availability of courts in a grid consisting of fixed one-hour time slots and courts.
[Normal] Create court bookings: Users can create Open, Locked or Private Coach bookings for available court and time-slot combinations.
[Normal] Join Open bookings: A second user can join an Open booking where only the first player position is occupied. Once the second player joins, the booking becomes Full and cannot accept another player.
[Normal] Manage own bookings: Users can view upcoming bookings and cancel their own eligible bookings according to the applicable booking rules.
[Normal] View coach availability: Users can view published coach availability by date and available one-hour time slots.
[Normal] Manage coaching availability: Coach users can select a date and publish one or more one-hour time slots during which they are available for private coaching.
[Normal] View upcoming coaching sessions: Coach users can view upcoming private-coaching bookings, including the player, court, date and time.
[Normal] Manage users and courts: Admin users can manage users and their statuses and roles, as well as create and edit courts and set courts as Active or Inactive.
[Heading 1.2] 3.2	Inputs
[Normal] Users will provide inputs to the system:
[Normal] Registration details required to register a USER account.
[Normal] Login credentials.
[Normal] Permitted personal information when editing a user profile.
[Normal] A selected booking date.
[Normal] A selected court and time slot from the availability grid.
[Normal] A booking type consisting of Open, Locked or Private Coach.
[Normal] Selection of an available coach when making a Private Coach booking.
[Normal] Confirmation of a new booking.
[Normal] A request to join an eligible Open booking.
[Normal] A request to cancel the user’s own eligible booking.
[Normal] A date and one or more fixed one-hour time slots selected by a Coach when publishing coach availability.
[Normal] User search criteria, edited user information, role promotions and account-status changes entered by an Admin.
[Normal] Court information and Active or Inactive status entered or changed by an Admin.
[Heading 1.2] 3.3	Processing
[Normal] The system will process user inputs and perform the following actions:
[Normal] User Authentication and Role Management: Create User accounts, authenticate registered accounts, determine the stored User, Coach or Admin role and route authenticated users to the appropriate dashboard. Role-specific access must be enforced by the backend.
[Normal] Live Availability and Booking State Processing: Calculate court availability for the selected date using court status, time-slot status, confirmed booking information and participant or coach information. Each court + date + time-slot combination is then displayed as Available, Open, Full, Locked, Private Coach or unavailable according to its current state.
[Normal] Court Booking Processing: Process Open, Locked and Private Coach booking requests. Before a booking is created, the backend must revalidate the court, date, time, player and, where applicable, coach information to prevent conflicting bookings.
[Normal] Open Booking Processing: Record the creator as Player 1 when an Open booking is created. When another eligible user joins, update the existing booking and participant information with Player 2 instead of creating another court reservation. Once Player 2 has joined, the booking becomes Full.
[Normal] Locked Booking Processing: Reserve the selected court, date and time for the booking creator without allowing another normal user to join the booking.
[Normal] Private Coach Processing: Identify coaches who have published availability for the exact selected date and one-hour time slot, allow the user to select an available coach, validate player and coach conflicts and create a locked player-and-coach booking when validation succeeds.
[Normal] Cancellation Processing: When an eligible confirmed booking is cancelled, change its status to Cancelled and remove its active reservation effect so that the court cell becomes available again.
[Normal] Coach Availability Processing: Save and publish the selected one-hour coaching availability so that it is displayed on the Coach Availability Notice Board and can be used when creating a Private Coach booking.
[Normal] User and Court Administration: Allow Admin users to search for, view and edit users; promote a User to Coach or Admin; change user status; create and edit courts; and change court status between Active and Inactive. Inactive courts must not be made available for new bookings.
[Normal] Data Storage: Store and update the core User, Courts, Time Slots, Bookings, Booking Players and Coach Availability data required by the booking system.
[Heading 1.2] 3.4	Outputs
[Normal] The primary outputs of the PukSquash web application are subject to change but will include:
[Normal] Display active courts and fixed one-hour time slots for a selected date. 
[Normal] Show booking states such as Available, Open, Full, Locked, Private coach and Inactive. 
[Normal] Display booking confirmations and validation errors. 
[Normal] Display a user's upcoming bookings and, in Phase 2, booking history. 
[Normal] Display published Coach availability and upcoming coaching sessions. 
[Normal] Display Admin management information for users and courts. 
[Normal] Phase 2 additionally displays payment results, booking management information and NWU team practice bookings.

[Heading 1.2] 3.8	Software interfaces
[Normal] PukSquash is assembled from a Vue 3 client, a Laravel REST API, Firebase Authentication and a Cloud SQL PostgreSQL database reached through Firebase Data Connect. The application therefore depends on several external software components for authentication, data storage and delivery to the user. The controlling principle across all these interfaces is that the frontend asks, the backend decides and the database protects the data. No external component, and in particular no component running in the student’s browser, is trusted to enforce a booking rule on the backend’s behalf. The following external software components are the main sources of dependence for the application:
[Normal] Vue 3 – Used as the frontend framework to provide the User, Coach and Admin interfaces, including court availability, bookings, profiles and management screens (Vue.js, 2026). 
[Normal] Laravel – Used as the REST API backend. Laravel handles business rules, role-based access, booking validation, availability calculations and conflict prevention before information is stored in the database (Laravel, 2026). 
[Normal] Firebase Authentication – Used for user registration, login, email verification and authentication. Firebase provides an identity token which is verified by the backend before protected functionality can be accessed (Google, 2026a; Google, 2026b). 
[Normal] Firebase Data Connect – Provides the connection between the application and the relational database used by PukSquash (Google, 2026c). 
[Normal] Cloud SQL for PostgreSQL – Stores relational application data such as users, courts, time slots, bookings, booking players and coach availability. PostgreSQL also supports database-level controls used to help prevent conflicting court reservations (Google, 2026d; PostgreSQL Global Development Group, 2026). 
[Normal] PayFast – Phase 2 – Used for registration payments and Private coach payments. Payment success must be verified by the backend before the related paid process is completed (PayFast, 2025). 
[Normal] Web browsers and operating systems – Because PukSquash is web-based, it will operate through modern browsers such as Chrome, Firefox, Safari and Edge on Windows, macOS, Android and iOS devices.
[Heading 1.2] 3.9	Communications interfaces
[Normal] PukSquash requires secure network communication between the user's browser, the Laravel REST API and the external services used by the application. Because the system processes personal information such as names, student numbers and email addresses, communication must be handled securely and in accordance with POPIA requirements (Republic of South Africa, 2013).
[Normal] Secure API communication – The Vue frontend will communicate with the Laravel REST API using HTTPS. This protects information transferred between the browser and backend from being transmitted through unsecured connections (OWASP Foundation, Inc., 2025). 
[Normal] REST API communication – Data between Vue and Laravel will primarily be transferred using REST API requests and JSON. These requests are used for operations such as retrieving availability, creating bookings, joining Open bookings, cancelling bookings and managing Coach or Admin functionality (Laravel, 2026). 
[Normal] Authentication communication – Firebase Authentication provides an identity token after login. This token is sent with protected requests and verified by the backend before the requested action is performed (Google, 2026b). 
[Normal] Email: outbound email is used by Firebase Authentication to verify a student’s NWU address during registration. The later-phase booking confirmations, booking reminders, cancellation notifications will use the same channel through the backend’s mail transport (Google, 2026a).
[Normal] Database communication – The backend communicates with the PostgreSQL relational database through the Firebase Data Connect / Cloud SQL environment. Database credentials and other sensitive configuration must remain on the server and must not be exposed through the frontend (Google, 2026c; Google, 2026d). 
[Normal] PayFast communication – Phase 2 – Secure communication with PayFast will be required for registration and Private coach payments. Payment results must be verified by the backend and not accepted only from information displayed in the browser (PayFast, 2025). 
[Normal] Network connectivity – PukSquash requires an internet connection through Wi-Fi, Ethernet or mobile data to access live availability, authentication and booking functionality. If the connection is lost, the system must not display a booking as successfully confirmed unless a successful response has been received from the backend. 
[Heading 1.2] 3.10	Design and Implementation Constraints
[Normal] The design and implementation of PukSquash will be subject to the following constraints to ensure that the system meets its functional and technical goals.
[Normal] PukSquash will be delivered as a responsive web application that must remain fully functional across desktop, laptop, tablet and mobile browsers. Core features such as the availability grid, booking flows, dashboards and management screens must adapt to different screen sizes without loss of functionality. Wireframes and responsive design principles will guide the interface design. 
[Normal] Because multiple Users may attempt to reserve the same court and time slot simultaneously, the system must prevent double bookings through backend validation and database-level integrity controls rather than relying on the frontend alone. The availability grid displays the current known state, but the backend must revalidate the selected court, date and time slot when the booking is submitted. 
[Normal] Phase 1 will use hard-coded booking rules in the backend. These rules include restrictions such as the booking window, maximum active bookings and cancellation conditions. Phase 2 will introduce Admin-configurable booking rules so that these values can be managed without changing the core booking process. 
[Normal] All personal information processed by PukSquash must be handled in accordance with the Protection of Personal Information Act (POPIA). Protected functionality must use authenticated access and role-based permissions, and sensitive information must be transmitted securely. 
[Normal] The agreed technology stack consists of Vue 3 for the frontend, Laravel/PHP for the REST API, Firebase Authentication for user identity and authentication, and Firebase Data Connect / Cloud SQL PostgreSQL for relational data storage. 
[Normal] Phase 1 will establish the core booking system, while Phase 2 will extend the application with PayFast registration and Private coach payments, booking and coaching history, configurable booking rules, Admin booking and time-slot management, and NWU squash team practice functionality. 
[Normal] The system must be designed so that future functionality can be added without changing the fundamental court, date and fixed one-hour timeslot booking model. 
[Heading 1.2] 3.11	Performance Requirements
[Normal] The following performance requirements are intended to ensure that PukSquash remains responsive and reliable across different devices and network conditions.
[Normal] Court availability must load quickly enough to provide an interactive booking experience. The availability grid must display the current state of all relevant active courts and fixed one-hour time slots for the selected date. 
[Normal] When a User confirms a booking, the system must perform the required validation and return a result without unnecessary delay. Correctness of the booking takes priority over displaying an immediate optimistic confirmation. 
[Normal] The system must correctly handle situations where multiple Users attempt to reserve the same court and time slot at approximately the same time. Only one confirmed booking may reserve a specific court, booking date and time-slot combination. Any conflicting request must fail safely and display an appropriate message to the User. 
[Normal] The same concurrency protection must apply when more than one User attempts to occupy the second-player position of an Open booking. Only one User may successfully become Player 2. 
[Normal] After a booking, cancellation, court-status change or other state-changing action, the affected availability must be refreshed so that Users do not continue to see outdated court information. 
[Normal] The system must remain stable during realistic periods of increased usage and must not allow increased traffic to result in duplicate, corrupted or inconsistent booking records. 
[Normal] Phase 2 team-practice bookings must also be processed reliably when a Coach selects multiple court and time-slot combinations. Team-practice override rules may bypass normal booking limits, but they must still prevent the reservation of inactive courts or already-booked cells.
[Heading 1.2] 3.12	Security
[Normal] PukSquash must protect user information, bookings and administrative functions through secure authentication and backend validation.
[Normal] Protected API requests must verify Firebase Authentication ID tokens. 
[Normal] User, Coach and Admin permissions must be enforced by the backend. 
[Normal] Users must only act as the authenticated account identified by the verified token. 
[Normal] Production communication must use HTTPS. 
[Normal] Firebase, PayFast and other backend secrets must not be exposed in the Vue frontend or public source control. 
[Normal] Personal information must be processed according to POPIA requirements. 
[Normal] Booking and Open booking join operations must be protected against race conditions and double booking. 
[Normal] Phase 2 payment success must be verified by the backend before the related process is completed. 
[Heading 1.2] 3.13	Usability
[Normal] PukSquash must provide a simple and consistent booking experience across desktop and mobile browsers.
[Normal] The booking process should require as few steps as possible while still confirming the selected court, date, time and booking type. 
[Normal] Availability states such as Available, Open, Full, Locked, Private coach, Inactive and NWU team practice must be clearly distinguishable. 
[Normal] Only actions that are valid for the current booking state should be displayed. 
[Normal] Private coach bookings must show only Coaches available for the selected date and time. 
[Normal] Error messages must clearly explain booking conflicts, unavailable slots, booking-rule restrictions and Phase 2 payment failures. 
[Normal] Important functions such as My bookings, Coach availability and cancellation must be easy to find from the relevant dashboard. 
[Normal] The interface must remain responsive and usable across desktop, laptop, tablet and mobile browser sizes.
